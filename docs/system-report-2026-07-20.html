§1

What this is, in one screen

A single-process, local Python app with two jobs that share one codebase:

  • Learn game theory + RL by building it. Every solver is written from scratch — the CFR family, exploitability/best-response, a heads-up subgame solver, a toy ReBeL — and each is verified against an independent oracle (PokerKit, OpenSpiel, brute force) rather than trusted.
  • Train you for live full-ring MTT poker. Import your own hand histories, get every decision graded against exact answer keys, see your leaks ranked by real EV loss, and drill exactly those leaks on a spaced-repetition schedule.

The load-bearing idea is grading honesty. The system refuses to pretend it knows things it doesn't: multiway postflop spots (where no trustworthy oracle exists) never get an EV-loss number — only frequency-deviation flags — and that rule is enforced by database triggers, not by convention. Every answer key is self-derived; nothing vendor-made ever enters the harness.

Why is “no ev_loss for multiway spots” enforced in the database rather than in code?
Because code paths multiply and conventions decay. There are two schema triggers — one on INSERT, one on UPDATE (the second exists because a review round found the first alone let the rule back in through updates). Any future code path that tries to write an EV number for a tier-3 grading gets a hard IntegrityError, and tests prove the triggers actually fire. A promise you can't violate is worth more than a promise you remember.

Storage, deliberately boring

SQLite, seven tables: imported_hands, gradings, drill_attempts, sr_state, solution_index, plus two the build earned — failed_hands (so a hand that fails to parse leaves a durable, named trace) and batch_queue (overnight tier-2 solves). Solve payloads live on disk keyed by SpotKey. The rule that keeps it honest: derived metrics are queries, never tables — leak rankings and skill gates are computed fresh from the raw rows, so they can't silently go stale.

§3

How it works, in depth

Each module below expands. The order is the order the system was built in — which is also the best order to read the code, because each layer is verified against the one before it.

M0 · Engine src/pokerlab/engine — the ground truth

A full no-limit hold'em rules engine: betting, side pots, all-in ladders, showdowns, tournament blinds/antes (including BB-ante), and the ICM/payout math. It is the one component everything else must trust, so it's the one component that's never trusted: a differential harness plays millions of seeded random hands simultaneously through this engine and through PokerKit (an independent open-source engine) and demands identical pot/stack/showdown outcomes.

Three axes run at 1M hands each in the soak (random full-ring, short-stack all-in ladders, BB-ante across 2–9 seats) — zero mismatches. The fast suite mirrors them at 20k. One documented carve-out: an “odd-chip” class (≤1% of hands) where the engines split a leftover chip between identically-ranked winners differently — a labelling difference, totals always agree. A review round proved this tolerance could never have masked a real bug: the one real chip bug found (a BB-ante refund error) produced deltas of ±100 chips against a tolerance cap of 3.

Why differential testing instead of hand-written test cases?
Hand-written cases cover the situations you thought of. A seeded random generator over millions of hands covers the situations you didn't — and poker's bugs live in the freak stacks: three-way all-ins with two side pots and a dead ante. The 20k fast axis detects a bug appearing in 0.02% of hands with ~98% probability; cutting it to 5k would drop that to 63%, which is why the review rounds refused every axis cut.
M1 · CFR + the exploitability instrument src/pokerlab/cfr — the learning heart

Counterfactual Regret Minimization is the algorithm family behind every modern poker solver. The idea: play the game against yourself millions of times; at every decision point, track how much you regret not having taken each action; shift probability toward high-regret actions; the average strategy over all iterations converges to a Nash equilibrium. The lab implements vanilla CFR, CFR+ (regret flooring — much faster), and MCCFR (sampled), verified on Kuhn and Leduc poker to NashConv ≤ 1e-3 (achieved 3.5e-4 / 4.7e-4), and cross-checked bit-for-bit against OpenSpiel's reference implementation.

Just as important is the exploitability utility built alongside it: given any strategy, compute the best possible counter-strategy and how much it wins. That number — NashConv — is the honest score for every solver in the lab. “It converged” is a feeling; “a perfect opponent beats it by 0.0003 chips per hand” is a measurement.

M1.5 · Chart engine src/pokerlab/charts — your answer keys

Two pieces. First, Malmuth-Harville ICM: converts tournament chip stacks into real-money equity, verified within 0.1% against reference values. Second, jam/fold Nash charts: for short-stack play (≤20bb), the game reduces to shove-or-fold, which is small enough to solve exactly with CFR+ — for chip-EV and, crucially, for ICM ($-denominated) at any payout ladder. Measured exploitability of the shipped charts: ≤ 2.7e-6 of the pool — effectively perfect.

These charts are the tier-1 answer keys. They're checked against a 33-entry hand-audited reference set (100% agreement) — but the audit is a sanity cross-reference only. The chart's correctness rests on the exploitability measurement, because per the project's rules no vendor chart may ever serve as an oracle.

Set the payouts to 1000 / 0 / 0 (winner-take-all). What happens, and why does it matter?
Every $/chip equalizes — ICM collapses to chip-EV exactly, because with only first place paid, your equity is just your probability of finishing first, which Malmuth-Harville models as your chip share. The flatter the remaining ladder, the more ICM pressure; the more top-heavy, the more it plays like a cash game. The R4 review measured this on the real solver: the bubble ladder solves nearly pure (1.8% of actions near-indifferent) while a top-heavy ladder mixes more than chip-EV (16.9% vs 12.3%).
M3 · HU subgame solver src/pokerlab/solver — real postflop answers

A heads-up postflop solver: given a spot (board, stacks, pot, bet grid), run CFR+ over the subgame tree with card-isomorphism bucketing (suit symmetries collapse the tree massively). Verified two ways: its internal best-response instrument matches exhaustive brute force to 1e-9, and solved rivers on the 25-flop fixture reach ≤0.5% pot exploitability (achieved 0.29% river, 0.42% turn+river). Solves are cached on disk and indexed by SpotKey — this is the tier-2 grading oracle.

Two recorded limits, deliberately: full-flop solves take ~1h each in pure Python, so the all-25-flops bar is deferred behind the planned Rust hot-loop port (the API seam is already in place); and tier-2 solves currently approximate both players' ranges as uniform — an approximation that, after R4, is disclosed on every grading it touches, all the way to the report page.

M2 · Drills + web UI src/pokerlab/drills, web — where you train

A drill is a spot plus an exact answer key. The scoring rule is honest about indifference: you're wrong only if your action's EV loss exceeds a threshold ε and the solution doesn't mix it at meaningful frequency — near-indifferent actions aren't punished, because punishing them teaches false precision. ICM drills grade in real dollars (ε converts by the ladder's $/chip). The harness proved a chart-perfect reference agent scores 100% (bar: ≥98%) and a deliberately bad agent scores 54% — both directions of the instrument verified.

The SM-2 spaced-repetition scheduler feeds you drills from your worst leak categories. A deliberate property discovered in review: for a struggling user its variety floor saturates at 4 categories regardless of syllabus size — it hammers what's bleeding. If you're answering well, it roams the full syllabus. If drills feel repetitive, that's information.

M4 · Hand-history pipeline src/pokerlab/hh — your real hands, graded

Parsers for PokerStars (auto-saved files) and GGPoker (Pokercraft exports, tolerant of its anonymized fields), a byte-faithful multi-hand splitter (chunks provably reassemble into the exact input file), and per-hand failure isolation: a hand that fails to parse lands in failed_hands — named by its hand number when the header revealed one, surfaced in the session summary and the report, never silently dropped, and its raw text kept so it can heal after a parser fix.

Then the tier router sends every single decision to exactly one oracle: tier 1 preflop/jam-fold → charts (exact, instant); tier 2 HU-postflop → solve library, misses queued for overnight batch solving, the session marked partial until its batch completes; tier 3 multiway → population-frequency flags only. The leak report separates exact from approximate tiers and ranks your top-5 leaks by EV-loss per 100 hands on the exact tiers only.

Your nightly cron imports 200 hands and 3 need overnight solves. What does the system promise about that session's report?
It's marked partial: true until those 3 solves land — scoped to that session's batch (R4 fixed the API, which had been reporting any DB-wide backlog as everyone's problem). The 197 graded decisions are readable immediately; the leak rankings will shift only when the batch drains. And if any hand failed to parse, it's in the report by name — a failed hand costing you silent data loss is the one outcome the pipeline was built to make impossible.
M5 + M7 · ReBeL and the spike src/pokerlab/rebel, spike — the research arc

M5 (Leduc, works): ReBeL's core idea is depth-limited solving — don't solve to the end of the game; solve a few streets deep and let a trained value network estimate what the leaves are worth, conditioned on both players' belief distributions. On toy-scale Leduc, everything the theory promises, happens: safe re-solving with oracle leaf values reaches NashConv 0.00112 (bar 2e-3), and the trained net (held-out RMSE 7e-4) is gated by agreement with the full solve.

M7 (tiny-HUNL, honest NO-GO): scaling the same recipe to a clipped hold'em — locally, on this machine, within the spend cap — fails the go bar at ratio ≈ 17×: net-driven resolving is 3.257bb exploitable vs the oracle baseline's 0.191bb, reproduced across seeds three independent times. What makes this the most instructive artifact in the repo is the post-mortem discipline: the intuitive explanation (“the net was queried on beliefs it never trained on”) was measured and rejected — on exactly the beliefs CFR queries, the net predicts within 1.09× of its held-out accuracy. A second mechanism (garbage predictions on degenerate beliefs leaking into regrets) was also measured and rejected (−0.3%). The gap stands honestly unattributed, with the true structural suspect recorded: training beliefs are sampled independently, but real leaf beliefs are strategy-weighted reaches CFR walked to — and no sampling parameter closes that; only self-play data generation (the real ReBeL loop) does.

M6 · Vectorized env + best response src/pokerlab/env — the RL substrate

A numpy-vectorized batch environment (~1.02M hands/min, 20× the target) that passes the same M0 differential suite through a single-env adapter — the env is proven equivalent to the engine, not assumed. Beside it, an exact tabular best-response exploiter: point it at a bot (e.g., the perturbation bots with VPIP/aggression knobs) and it computes the maximally exploiting counter-strategy, verified identical to brute force. This is the substrate for any future “train an exploiter against a player pool” work.

§5

Insights — what the results let us infer

About poker

  1. “Solver sharpness” is a property of the payout ladder, not of ICM. Measured across four ladders: the bubble structure solves nearly pure (1.8% of actions near-indifferent, and the wrong ones lose 1.85× the threshold at the 10th percentile), a flat ladder solves perfectly pure (0.0%), while a top-heavy ladder mixes more than chip-EV does (16.9% vs 12.3%). Training read: the bubble is where study pays most — answers are close to deterministic, so mistakes there are both most punishable and most learnable. Deep final-table play against top-heavy ladders is inherently mixed; expect (and forgive) lower drill accuracy there.
  2. The $-per-chip asymmetry is large enough to reverse decisions. On the bubble fixture the chip→dollar conversion runs ~25× between contexts (and is provably scale-free — a property of Malmuth-Harville's linearity, not the pool size). Chip-EV instincts imported from cash games are systematically too loose near bubbles.

About the RL experiment

  1. Model accuracy was never the bottleneck — data distribution was. The spike's value net predicts well even on the sparse beliefs CFR actually queries (1.09× its held-out error) — yet the agent it powers is 17× more exploitable than the oracle baseline. Two intuitive mechanisms were measured and excluded. What remains is structural: training beliefs were sampled independently; real leaf beliefs are strategy-weighted reaches the solver walked to. No tuning parameter aligns those distributions — only generating data along the solver's own trajectory (true ReBeL self-play) does. This is the local, reproducible version of a deep RL lesson: where your data comes from beats how well your model fits it.
  2. Training loss is not a proxy for playing strength — proven, not asserted. A run with lower value-net loss produced 24% worse exploitability. The go/no-go gate was measured on exploitability directly, which is why the NO-GO verdict survived three attempted explanations while the numbers never moved.
  3. Unsafe subgame decomposition fails at any scale. The Leduc net-driven ceiling (~0.42 NashConv from spurious round-1 equilibria) is a property of the decomposition, not of compute — which is precisely why ReBeL's “safe re-solving” machinery exists, and the lab's safe variant hits its bar on the same game.

About building with verification

  1. The seams between components caught the worst bugs. Both P0-class defects in the product lane were found by driving the user's surface (concatenating fixtures the way real PokerStars files arrive; importing twice the way cron does) — not by any unit test. Its mirror: every false alarm came from probing a narrower input than the invariant assumes. Same instrument, both directions.
  2. A measured number that lives only in prose decays silently. The scheduler's variety floor (4) sat in a comment until R4 derived it from its governing constant and pinned it with a test verified at six parameter values. Prose degrades; only a test fails.
  3. Structure beat size on performance. The suite grew +52% in tests while getting 27% faster (52.9s → 38.6s) — because the fix was parallelism-shape (xdist with the differential's internal pools divided by worker count), chosen from a lever order pre-registered before the breach measurement existed. Deciding the order before knowing the number is what kept a detection-power-destroying shortcut (halving a differential axis) off the table.

§6

Next steps, in the order they unlock each other

  1. Merge PR #1 and start the habit: the plan's own skill gate is training-daily, tracked as a KPI. Import your real PokerStars/GGPoker sessions (nightly cron on pokerlab-import + pokerlab-batch), and let the leak report tell you what to drill. The system is complete for this today.
  2. The Rust port (seams already in place, drop-in by design): the M3 solver hot loop first — it converts full-flop solves from ~1h to minutes, which unlocks the deferred all-25-flops bar and makes overnight tier-2 batches effectively instant. The M6 env port (pyo3) rides the same pattern.
  3. The ReBeL self-play loop — the one structural gap the spike proved matters: generate value-net training data along the solver's own trajectory instead of by independent sampling. The closure gate (v7_invariant.py, preserved at ~/pokerlab-data/reviews/) is designed to stay failing until exactly this lands; if it ever passes without this work, distrust the gate, not celebrate.
  4. Widen the syllabus when tier-2 drills arrive: resteal, ante-adjusted, final-table ladders, postflop drills from your own solve library — and the deferred range-grid UI becomes worth building at the same moment, since those are the drills whose answers are range-shaped.
  5. Grow the population table from your own imported hands (the promised generator-priors and bot-target consumers are recorded as deferred until these drills exist), and point the M6 exact exploiter at population-styled bots to study maximally exploiting weak fields — the step beyond Nash.

Everything above is recorded in docs/PLAN.md rev 3.3 with its deferral rationale — none of it is a loose end; all of it is a decision.
